> 状态：**已定稿，待开工（Phase 1 内核）**
> 关联：docs/REVIEW_2026-08-05.md（审查存档，3 个 P0 先行修复）
> 决策（已确认）：**继续当前 repo，不重开 v3**。保留数据库/schema/prompt 经验，将运行时重构为**统一的多角色场景引擎**。
> 审查日期：2026-08-05

## 1. 目标 & 统一模型

把约会、群聊、剧本、多人剧本、任务、探索六种交互**统一成同一套"场景"**。

**统一模型：一个场景 = 一个地点 + 环境旁白 + 若干在场NPC（可互动）**

| 场景类型 | 同行NPC数 | 说明 |
|---|---|---|
| 探索 | 0 | 纯环境，可偶遇NPC → 偶遇后加入同行 |
| 约会 | 1 | 单同行者 |
| 群聊 | N | 多同行者 |
| 剧本 / 多人剧本 | 1 / N | 剧本规则附加 |
| 任务 | 1 + 执念路人 | quest_npc 是特殊路人 |

**核心洞察：这些场景的差异只有一个参数——同行NPC数量。** 一行代码动态化，而非六套实现。

> 用户明确否定探索现用的"偶遇 + 环境分离"两套式，要求**环境与常驻NPC融合成单一场景**（环境里就有人，人就在环境里，不是先描写环境再偶遇拉走）。

## 3. 目标架构

### 3.0 实施策略：新写干净内核 + 逐个接入替换【已决】

**结论：不原地硬捏旧代码，而是新写一版干净的场景内核，再把约会→剧本→任务→探索逐个"接入"进来，旧路由验证后逐步废弃。**

为什么新写优于硬捏（在无测试覆盖的代码库上）：
- 现有 `conversation.ts`/`sms.ts`/`scenario.ts` 是 4 份互相复制的 turn 编排，各自带微妙的 bug（scenario retry 缺 need_search、群聊 speaker 无容错）。**原地硬捏 = 同时在这 4 份副本上做抽象，很容易从一个坑挪进另一个坑。**
- 新写 = 干净自包含的内核，新旧边界清晰：新内核不依赖旧路由内部逻辑，验证一个、替换一个，旧系统持续跑。
- 这正是"保留 schema/prompt、重写核心交互层"的含义：**schema 表和 prompt 是资产，4 份复制的那层 turn 编排是负债——负债直接扔，资产保留。**

**必须守住边界（别把资产当负债扔了）**——"新写"不等于"全扔重整"：
- ✅ **直接复用（资产）**：`prompt/builder.ts` 已调好的 `generateReply`/`generateGroupReply`、`normalizeReply`、`REPLY_SCHEMA`（environment/quest_npc_line）、embedding 检索、prompt 模板；数据表 `messages`/`session_participants`/`conversation_sessions`/`location_npc_access`。
- 🆕 **重新写（负债）**：只有那层"turn 编排"（旧代码 4 份复制、各有 bug 的部分）——send/retry/nudge/群聊 turn 的调度、记忆/回溯裁剪、speaker 容错。

一句话：**新写"编排内核"，复用"生成器/表/prompt"，接口逐个接进来。**

**落地映射到 Phase**：
- Phase 1 就是"新写 `runSceneTurn` 内核 + 先接约会"（新内核写出，约会路由切到它）。
- Phase 2-3 是"剧本/任务/探索逐个接入新内核"，接入一个、验证一个、废弃旧的那个对应 turn。
- 不是"重构 4 份代码合成一份"，是"写第 1 份干净的，然后 4 个系统都指向它"。

### 3.1 统一场景 turn 内核

```
runSceneTurn({
  sessionId,
  location,          // 当前地点（含 current_location 移动）
  companions,        // NPC[] —— 同行者（0~N 个）
  residentNpcs,      // NPC[] —— 该地点常驻路人（从 location_npc_access 读出）
  rules,             // 场景规则：剧本 stats / 任务 quest_npc / 纯闲聊
  playerMsg,         // 玩家输入
})
```

`companions + residentNpcs` 合并成**统一的"在场角色表"**，喂给多角色 prompt，`npc数量` 是运行时数据而非代码分支。

### 3.2 输出契约：有序 beat 序列【已决】

**统一生成 schema 收敛为一张 beat superset 表**（消除单聊/群聊两套 schema 之争）。

> 注：§3.3 定案为**两阶段**后，导演只产 `intent`（编排），`content`（实拍）由演员逐拍生成。故 beats 的**大纲形态**是「kind + speaker + intent」（导演），其**演出形态**才是带实拍内容（演员）。下表同时给出两态：

```
# 导演产出（大纲，只编排不演；§3.3）
beats: [
  { kind: 'narration', intent: "水边的景色，夕阳把海面染成橘色，交代环境给角色可响应的素材" },
  { kind: 'character', speaker: "商贩", intent: "热情招揽玩家，顺带和男主较劲" },
  { kind: 'character', speaker: "男主", intent: "护着玩家，替她挡掉商贩的招揽" },
  { kind: 'narration', intent: "把话头抛回玩家，等玩家拿主意" },
]

# 演员演出后（落库形态）
beats: [
  { kind: 'narration', content: "水边的景色，夕阳把海面染成橘色…" },
  { kind: 'character', speaker: "商贩",  content: "新鲜烤鱿鱼~来一串？" , internal:"…", internal_notable:false},
  { kind: 'character', speaker: "男主",  content: "要不要试试？这家挺好吃的。" },
  { kind: 'action',    type: 'move',   to: "海边小吃街" },
]
```

- **`kind` 类别字段去掉一切维度割裂**：旁白=`narration`、角色说话=`character`（带 `speaker`）、动作=`action`。`action` 的子类型包括 `move`（移动）和 `search`（搜索回忆）。**数值结算不单独成 action 拍**——它并进 `narration` 拍（旁白携带 `fn`/`args` 自己调用函数 → 得真实值 → 照述，见 §3.3.7）。
- **导演版 beats 用 `intent`（编排意图），演员版用 `content`（实际内容）+ `speaker`。**
- **`environment`/`quest_npc_line` 不再是特殊字段**，分别退化为 `narration` beat 和 `speaker=路人` 的 character beat。
- **`need_search`/`current_location` 变成动作 beat**，统一内核按序执行。
- **单聊=群聊**：单聊就是 beats 里只出现一个 speaker，天然同 schema。
- 可选字段空着完全正常——不存在"两套 schema 选哪套"的纠结。

### 3.3 两阶段生成：先"导演"编排，再逐 beat 演出【已决】

**动机（防上下文污染 / 人设漂移）**：一次 LLM 输出所有角色的台词，模型要同时"扮演"多个角色，人设互相漂移（越到后文越受前文角色影响）；旁白与对话混生也会互相带偏。**逐 beat 逐个角色 = 每次 LLM 只喂"该角色人设 + 到节点为止的上下文"，只让它说这一句话，每个角色专注自己。**

**第一阶段——导演（大纲）LLM**：只做编排，不写台词。
- 输入：scene（location+rules+residentNpcs）+ 本轮上下文 + 在场角色表
- 产物：`beats[]`，每拍只含 `kind`/`speaker`/`intent`（这拍谁、对谁、想推进什么情绪/方向）——**不含具体台词文本**

**第二阶段——演员（逐beat）LLM**：每个 beat 单独一次调用。
- `system` = 该角色人设 + 本轮场景上下文（旁白拍 = 镜头/环境语言人设）
- `user` = 大纲里该拍的 `intent`（"往哪引、什么情绪"）
- 产物：该角色这一句 → 按 beat 顺序分表入库

**分工**：第一个 LLM 通晓全局当"导演"，第二个 LLM 各入戏当"演员"——导演知道全场，演员只认自己那几句。

**导演是自由编排者，不是套模板**：导演拿到"三折叠记忆（玩家行为史/关系阶段）+ 最近对话 + 场景状态/值（若有数值系统）+ 场景规则目标"后，**自由决定这一轮怎么演**——可以是纯对白（角色↔玩家直接交流）、行动叙事（角色主导动作+环境展开）、事件流（如直播刷屏旁白）、路人介入，或它们的任意组合。beats 的**顺序和组合完全自由，无固定形态/固定顺序**。核心要求只有两条：
- **默认从简**：大多数回合就是角色↔玩家直接交流，不加旁白、不叫路人、不硬加戏。
- **按触发加料**：仅在特定情形才加——场景转换/新事物出现（旁白建场）、两人冷场/尴尬/话题枯竭（叫路人撑场）、需要强调/剧情需要（旁白定调）、数值系统存在（导演定值，见 §3.3.7）。
- **无固定顺序**：麻烦旁白/路人/行动都只是"按需的例外"，不是"每轮的常规"。导演不是从几个预设形态里挑一个，而是自由调度任意 beats 组合。

> **Spike 已验证（xiaosuan-8，3 关）**：纯固定分镜 + 逐拍即兴，在「温吞吃醋 / 激烈争吵 / 玩家中途插话」三类场景全部自然 hold 住，人设不漂移、能自然收口回玩家。**结论：导演"实时监视/救场"当前不需要实现**——固定分镜 + 逐拍即兴已足够，导演介入降级为可选增强（将来需要时再按"信号触发"做）。spike 脚本在 `apps/server/scripts/`。
>
> **gemma 对照（docs/gemma-test-results.md）**：同一批固定分镜 + 逐拍即兴在 gemma 上同样成立——三股声音（旁白/商贩/星回）清晰分离、人设不崩、收口自然。**gemma 的台词更偏"动作描写 + 内心戏"文学化表达——这正是无限心动选型 gemma 的原因（大量动作描写 + 内心戏，内心戏作收费 feature），属设计取向而非缺陷。** 演员模板需按模型给更强的输出约束（星回的 prompt 需强调"只说一句口语、动作神态归旁白"）。
>
> **导演/演员模板（已实现并实测样本）**：`apps/server/src/prompt/templates/scene.director.txt`（导演只编排、不写字）、`scene.actor.txt`（演员只演自己、内外解耦）。导演样本已跑通产出合理 beats；演员样本台词/内心分离、内心戏由角色自我驱动。

### 3.3.1 节奏上限与驱动规则【已决】

1. **节拍上限**：单轮上限设得较宽（如 ~12 拍），但 prompt 明确要求导演"**尽可能短、别晾着玩家**"——上限是保险，常态靠 prompt 引导求短。
2. **自然收口回玩家**：收口是"话头最终落在玩家"的**自然结果**，不是"必须有一个收口拍"。对话型轮里角色说完话头自然在玩家；事件/数值型轮(如直播刷屏)其内容本身就是给玩家的，无需机械"抛回"。导演**不需要主动判断"这轮是什么场景再决定要不要收口"**——默认从简、不硬加旁白收口拍。spike 已验证可自然做到。
3. **玩家发言时机（不打断）**：剧情演绎期间**不显示输入框**，玩家不能中断。玩家看完整轮 → 下一条输入。整轮 = 一次完整流程。
4. **retry/undo 语义（整轮为最小单位）**：`从玩家上一次发言起（无发言=从开头），到本轮结束`的整个剧情是**完整流程，当前不可再拆**。retry/undo 以整轮为单元，不做"拆到单拍"。将来有按拍拆的需求再议。
5. **戏份权重由导演决定（非固定一视同仁）**：常驻路人 vs 同行者的节拍预算**不硬性平均**，由导演按剧情需要分配。例：角色与玩家冷战时，路人戏份可更多（撮合/缓和），主角退为背景。同行者/路人仍是同一"在场角色表"，只是权重是导演的编排自由度。

> 以上 5 条中，第 1-2 条（节奏上限 + 必备收口）是 Phase 1 内核的硬约束；第 3-5 条在 Phase 1/3 落地时执行。C（retry 按整轮）、D（路人权重点导演）属后置，不阻塞 Phase 1。

### 3.3.2 玩家创建的场景 NPC 上限【已决】

- **场景 NPC 是玩家创建、和地点挂钩的**，数量天然有限（玩家自己经营自己的世界，不会海量）。
- **上限在创建时检测**（不做运行时裁剪）：
  - 玩家给某地点**创建/添加 NPC** 时，检查该地点已有常驻 NPC 数。
  - 达到上限 → 拒绝创建，提示玩家**联系管理员删除已有的常驻 NPC**（玩家侧无删除权，删除权在管理员）。
- 与 §3.3.1 D 的"在场裁剪"区分：那是在场每次调用多少；这里是**该地点最多登记多少**。两者都管，前者运行时、后者创建时。

### 3.3.3 路人的行为模式：话题/撑场发力者【已决】

- 路人**不是"默认旁观"也不是"自由参与"**，而是**"找话题/撑场"的特定发力者**。
- **发力时刻**：当场景陷入冷场/话题枯竭（如两人走路有一搭没一搭、气氛尴尬/沉默）时，**由导演把节拍交给路人**，让路人接话、引话题、缓和气氛、推进。
- 即：路人是导演手里的"气氛调节器"——平时低存在感，冷场/需要推进时才被点名上场。这是导演调度的一个具体触发规则。

### 3.3.4 is_group 废除，改用「角色数 + 路人数」【已决】

- **废除 `is_group` 布尔列**（读写不再依赖它）。
- **替代**：用两张天然区分的表推导——
  - **角色数（同行者）** = `session_participants` 行数（这场戏跟着玩家的主角团）
  - **路人数** = `location_npc_access` 该地点的常驻 NPC 数（可出场的路人）
  - "是不是群聊" = `角色数 ≥ 2`；"场景有几人" = 角色数 + 路人数。
- **兼容**：旧数据 `is_group` 列先留着不删（不动历史），新代码不再读写，靠推导。稳定后清理。
- 数据结构本就天然区分两类（participants 按 session、location_npc_access 按 location），无需额外标记。

### 3.3.5 内心戏生成原则：角色自我驱动，与导演 intent 解耦【已决】

**背景**：内心戏（`internal`）是无限心动针对 gemma 选型的关键设计（大量动作描写 + 内心戏，内心戏计划作收费 feature）。现有代码已实现完整心声机制：prompt 让模型产出 `internal`（内心独白）+ `internal_notable`（是否值得给玩家看），前端仅当 `internal && internal_notable` 才显示"⚡心声"按钮、点击展开、`internal_viewed` 记录已看。**数据上内心戏天然与台词 `text` 分离，收费只需渲染侧隐藏按钮，无需改生成逻辑。**

**在拍模型中的落点【已决】**：
- **拍里没有内心戏**——内心戏**不是独立拍**，也不由导演编排；它是**角色"说话"那一刻自带的**（附着在 `kind:'character'` 拍上），复用现有 `internal`/`internal_notable`/`internal_viewed` 字段。
- **动作描写归旁白拍**（`kind:'narration'`），台词+内心戏归角色拍。

**关键原则（防"导演让我这么说"的尴尬）【已决】**：
- **解耦**：导演的 `intent` 只决定角色的**外在言行方向**（推进剧情）；角色的**内心戏由"角色自我"驱动**（性格、对玩家的感情、过往、此刻真实的反应），不服从导演意图。
- **允许反差**：说出口的（顺从导演推进）与心底的（角色真实反应）**允许、且应该**不同——这正是现有 prompt "internal 可和表面行为形成反差"的意图。
- **生成依据**：组装演员上下文时，内心戏的主导信息 = 角色自我摘要（性格底色/关系/过往），而**不是导演的 intent**。导演 intent 只进"外在言行"部分。

> 防尴尬的根源：把内心戏"附着在角色说话时、由角色自我带出"，而非"独立拍由导演编排"——前者给了内心戏脱离导演的空间。这条已按用户确认定案。

### 3.3.6 记忆分层与归属【已决】

**上下文实时组装（同步）**：导演/演员调用前**同步**拼好上下文，不能依赖未跑完的异步。热窗原文保证"新鲜接住最新话头"，近期段摘要保证"有长度"。异步只用于非当下环节。

**记忆三层（每个 A 的名下）**：
| 层 | 内容 | 何时折叠 | 折叠去 |
|---|---|---|---|
| 热窗 | 最近 1-2 轮原文（逐字） | 移出热窗时 | → 近期段摘要 |
| 近期段摘要 | 中程压缩，**按角色保留归属**（谁说的/谁的内心不混淆） | 老化 | → 增量全摘要 |
| 增量全摘要 | 整对话滚动总览（角色↔玩家） | 场景末/关键点翻新 | 保留 + 跨场靠 embedding |

关键：折叠**逐层接力**（热窗→近期段→全摘要），不重复扫全部；每层**逐角色保留归属**防张冠李戴。

**摘要由谁生成**：独立的**归档/记忆 agent**（无戏份、无角色卡、只做事实/归属/骨架的转录），**不是导演**（导演只面向未来的祈使，写摘要会带剧本视角、污染）也不是演员（无全局）。复用现有 chronicle 折叠通道，异步触发，不占对话延迟。

**谁跟谁走、活多久**：
| 角色 | 记忆键 | 谁写 | 生命周期 | 用途 |
|---|---|---|---|---|
| A（角色） | 角色↔玩家（热窗/近期段/全摘要） | **A 自己** | 永久，每场增笔 | 关系传记、人设 |
| 导演 | 本场编排/氛围/走向 | 导演自己 | **场末折叠成"约会/场景摘要"独立存档**，供按场景回忆 | 场记、按场景召回 |
| 场景NPC | **无记忆** | — | 每次都是新人（工具人/氛围组，摊贩/工作人员等） | `location_npc_access.activity` 够用，不动表 |

**导演跟场景走，用完即弃（不跟玩家走）**：一场开启时读本场在场角色的记忆 → 维护本场记忆 → 场末把本场折成"约会/场景摘要"存档，导演自身不跨场累积。**这样从结构上杜绝露馅**——导演读的本来就是本场在场者的记忆，跨场/其他角色（如 B）的信息根本没加载，无需事后过滤层。

**场摘要的用途 = 玩家可读的回顾，不是导演的编排输入**：场末生成的"约会摘要"是给**玩家**看的回顾存档（回忆/时间线用），**导演看不到、也不投入任何场景的编排**。导演每场只读**本场角色记忆**。这样场摘要把"这一场"沉淀下来供玩家回顾，但永远不会被导演/其他角色读到 → 跨场私密不会经场摘要泄给旁边的角色。导演的编排输入只看本场在场角色的记忆，与玩家可见的场摘要完全分离。

**场景NPC 露馅防线**：NPC 无记忆；角色/导演的跨场私密不进入 NPC 渲染。NPC 只在自身地点/共享场景出场，天然满足。

> 露馅问题的根源与解法：全局编排（导演知道玩家和 A/B 都约过会）若灌给"单角色的演员 A"就会穿帮。解法不是过滤层，而是**导演每场只加载本场在场者上下文**（结构性隔离），跨场私密除非玩家主动带入，否则不进这场。

### 3.3.7 数值与旁白的协同：导演定值，函数算值，旁白报结果【已决】

**背景与踩坑**：数值系统（直播赚钱还债/侦探破案计分等）由 `scenarios.stats_config`（数值定义）+ `scenario_sessions.stats_state`（当前状态）承载。既有实现用 `judgeStats`（一次独立 LLM 调用）从对话文本里"另判"数值增减。**坑**：当数值独立判定而旁白自由叙述时，两者各说各话——如旁白"王富贵刷了深渊礼包5万块"、裁判却只判 +20，玩家立刻出戏。根源：同一件事有了**两个权威来源**（旁白文本 vs 数值判定）。

**数值系统定位【已决】= 纯娱乐、可随便口胡，不强制严格数值**：这是"写的玩的、纯看乐"的轻系统。**不加校验层、不锁档位、不做硬核经济**。真有特别严格的数值（竞技/排行）将来再说。所以数值函数**不是"拦截/校验导演数字的闸门"，而是"执行导演定的数 + 给旁白一个权威的真实结果"**。

**三幕机制【已决】：导演定值 → 函数算值 → 旁白报结果**：
```
玩家行为（唱了首歌 / 整了个活）
  → 导演定值：{ fn:'applyDebtChange', args:{ delta:-50000, reason:'大额打赏' } }   ① 导演自由定 delta（可口胡，纯娱乐）
  → 函数算值：applyDebtChange(-50000) = debt 50000→0                            ② 函数忠实执行，算出并返回真实数值
  → 旁白报结果：生成"王富贵刷了个深渊礼包5万，负债还剩 0"                         ③ 旁白引用函数返回的真实结果（after/delta）
  → 内核落库：stats_state.debt 真的 0                                             ④ 真实变更，不穿帮
```
- **① 导演自由定值（可口胡）**：导演直接给 delta（可正可负），想多大多大。数值系统是玩的，导演数字怎么编都行。
- **② 函数算值（忠实执行）**：函数把导演定的 delta 应用到当前状态上，算出并返回**真实** before/after/delta。函数是"算账+报数"的执行器。
- **③ 旁白报结果（关键）**：旁白**必须引用函数返回的真实结果**（after/delta）来写，不得另编数字。这是治"5万 vs 20"的核心——旁白报的永远是函数算出的真实数，与落库天然一致。**导演怎么口胡都行，但旁白/落库永远是一条数**。

**结算函数注册表**：每个数值对应一个作者注册的结算函数（`applyDebtChange`/`applyCashChange`/`applyHeat`）。
```
建剧本时（作者）定义 stats_config：
  { name:'debt',  fn:'applyDebtChange',  rules:'打赏→减债；导演自由定 delta' }
  { name:'cash',  fn:'applyCashChange',  rules:'礼物→加现金；导演自由定 delta' }
  { name:'heat',  fn:'applyHeat',        rules:'表现好→涨热度；导演依表现自由定 delta' }
```
- 导演只能调用**存在**的函数（函数名必须来自 stats_config），这是唯一约束——不是为了管住数值大小，而是函数名要对得上注册的执行器。
- 数值函数是**内核可执行的真实函数**（不是 LLM 口胡），执行后落库 `stats_state`，不穿帮。

**结构落点（beats 内，治"5万 vs 20"）**：数值结算**不单独成动作拍**，而是**并进旁白拍**——一个 narration 拍自己携带 `fn`/`args`，由旁白"调用"函数。这样**一个拍内原子完成**：执行函数 → 得真实值 → 旁白照述，不靠"紧随其后"的位置耦合：
```
beats: [
  { kind:'narration', fn:'applyDebtChange', args:{ delta:-50000, reason:'表现极佳' }, intent:'这拍先结算债务减少，再照述真实的负债变化' },  ← 旁白拍自己携带 fn+args（导演自由定 delta）
]
```
- 导演产出**单个 narration 拍**，内嵌 `fn` 和 `args`（自由定 delta）。内核处理该旁白拍时：先执行 `fn` → 算出并落库真实值 → 把 `changes`（before/after/delta）注入 → 再由旁白照述真实结果。
- **防"5万 vs 20"的关键**：旁白生成时**必须基于函数算出的实际结果**，旁白没有任何"自由编数字"的空间。导演可以自由定 initial delta（可口胡），但**旁白和落库只认函数算出的真实值**——所以两者永远一致。因为结算和照述在同一旁白拍内原子完成，根本不存在"另一条旁白漏注入"的路径。

**何时启用**：
- 仅在**有数值系统**（`stats_config` 非空）的剧本启用"导演定值 + 函数算值 + 旁白报结果"。
- 普通纯闲聊场景（约会）无数值系统，导演完全不产出数值，旁白纯叙事（"夕阳很美"），不加任何数值环节。

**与 judgeStats 的关系**：取消独立的 `judgeStats` 二次判定调用——"这波触发了数值变更、数值是多少"由**导演**在编排时自由判定，数值变化由**注册函数**忠实执行算出真实结果并由旁白照述。省一次 judgeStats 调用，且叙事与数值天然一致。

### 3.4 数据流（一个 turn）

```
玩家输入
  → 读 session + location + companions(从 session_participants)
  → 读 residentNpcs(从 location_npc_access，本地点在场)
  → 组装 在场角色表 = companions + residentNpcs
  → 【导演】buildSceneSystemPrompt(规则+旁白引导+在场角色) → 一次 LLM 出 beats[](kind/speaker/intent)
  → 【演员】对每个 beat 单独一次 LLM（system=该角色人设+上下文, user=intent）→ 该句台词/旁白/动作
  → 按 beat 顺序执行动作（move/search）+ 分表入库（assistant(speaker)/narration/quest_npc）
  → 记忆折叠 / 回溯(undo/retry) 统一按 session 范围
```

**落库原子性（事务边界）**：一个 turn 的所有写入——玩家消息、旁白、各角色台词、数值结算（`stats_state` 变更）、位置变更（move 改 current_location）——必须在**同一个数据库事务**内完成（BEGIN … COMMIT/ROLLBACK）。任一写入失败 → 整体回滚，不留"半截状态"。**否则会出现旁白说"负债-50000"但数值实际没扣、或消息入了一部分但数值没变这类不一致**（同 §3.3.7 治的"5万 vs 20"是同一类问题的另一面）。

### 3.5 单聊 = 群聊（数据层已兼容）

单聊就是 `companions=[对方]`、`participants=[对方]`、`is_group` 可保持现语义。**数据层（session_participants/messages.speaker）已支持**，无需迁移。价值：删除单聊专用生成器，`generateReply` 的复制逻辑一并收敛。

### 3.6 「当前地点」+「场景规则」合并为统一 Scene【已决】

**结论：可以合并，且应该合并。二者本就不在同一维度——一个是"状态"，一个是"配置"，合并后正好收敛成 Scene 实体，无需再独立理解两个概念。**

- **`current_location` 是状态**：`conversation_sessions.current_location_id` 一列，表示"这个会话此刻在哪"，随移动更新，是跟着会话走的可变指针。
- **场景规则是配置**：`buildMissionWorldContext` 拼出的一段 prompt 文本（世界+环境+氛围+规则+任务目标+执念持有者+地标+居民+阶段化推进指令），来自 `missions`/`scenarios` 的 `worldview`/`rules`/`stats_config` 等字段。
- **纠缠根源**：任务场景把"环境 summary、地标、居民"也塞进规则文本，等于**把"地点该长什么样"罩在了"规则"里**，而 `current_location` 只剩一个位置 id——这正是"可以合并"的直觉来源。

**合并后模型**：

```
Scene = 一个持久的"场景"实体
  ├─ name / summary / tone            ← 环境旁白（现散在 world.summary / scenario.worldview / locations.summary）
  ├─ rules / lore / world_tension     ← 场景规则（现散在 mission.rules / scenario 世界观）
  ├─ resident_npcs[]                  ← 常驻/可偶遇NPC（现散在 mission.minor_characters / location_npc_access）
  ├─ stats_config                     ← 剧本数值系统（现 scenario 专属）
  └─ 移动指针：会话只需 current_scene_id，不再各自维护
```

**现有代码映射**：

| 现状 | 合并后 |
|---|---|
| `conversation_sessions.current_location_id` | `Scene.id`（会话指向所在场景，LLM 移动时改这个指针） |
| `buildMissionWorldContext` 里的 world/landmarks/居民 | `Scene` 的环境 + 地标 + resident_npcs 字段 |
| `missions.worldview/rules/lore` | `Scene` 的 rules/lore（任务 = 在这个场景里挂一场任务） |
| `scenario.worldview/stats_config` | `Scene` 的 rules/stats（剧本 = 在这个场景里挂一段剧本） |
| `mode='chat'/'scenario'/mission` | 退化为 Scene 的"活动类型"字段，不再是三条并行代码路 |

**边界提示（不硬并）**：scenario 特有 `stats_config`（数值掷点）、mission 特有 world 层级的复杂结构（名利场/深空）是场景的**附加规则层**，不该硬塞进一个扁平 location。建模是 Scene **包含** location 维度 + 规则维度，而非把 location 塞进规则或反之。

**Phase 落点**：Phase 1 骨架就以 `Scene` 为单一入参单元（location + rules + residentNpcs 合一），而不是 `runSceneTurn` 里分别传 location 和 rules 两个概念。

## 5. 关键风险（会吃掉估量，先说清）

1. **群聊 speaker 容错**（REVIEW #16）：放开路边路人后，LLM 输出 speaker 的识别/容错要重做，否则张冠李戴。最大坑，约 1 天。
2. **记忆/回溯一致性**：旁白与路人消息混入后，retry/undo 的裁剪范围要统一（现 conversation 删 assistant/quest_npc/narration，scenario 删 assistant/narration——不一致）。需先修再叠加。
3. **常驻NPC数量失控**：一个地点挂太多常驻NPC会让 prompt 爆、每次生成变慢变贵。需上限 + 按在场动态裁剪。
4. **P0 挡路**：creation FK / mission 列名不修，新增常驻NPC写入会踩成长线。
