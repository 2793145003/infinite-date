## 🔴 P0 — 阻断级 Bug（上线即坏，已逐行独立验证）

### 1. mission.ts 查询不存在的列 → NPC 同伴永远拿不到权限奖励
- **位置**：`apps/server/src/routes/mission.ts:607-610`
- **问题**：`evaluateWorldMission` 中查询
  ```sql
  SELECT character_instance_id FROM character_instances
  WHERE player_id = ? AND character_id = ? AND is_active = 1
  ```
  但 `character_instances` 表**没有 `character_id` 列**（真实列为 `id/player_id/source_type/source_character_id/character_data_id/instance_no/is_active/created_at`），只有 `source_character_id`。该 SQL 必然抛 `no such column: character_id`，被内层 `try{}catch{}` 静默吞掉。
- **结果**：注释/设计写的"NPC 同伴也获得权限"是假的——世界任务结束后同伴永远拿不到权限奖励（`grantCharacterPermission` 永远不会执行）。
- **修复**：改 `WHERE player_id = ? AND source_character_id = ? AND is_active = 1`（参照 `creation.ts` 的 fork 逻辑）。
- 状态：❌ 未修复

### 2. creation.ts 私有角色创建必然外键崩溃
- **位置**：`apps/server/src/routes/creation.ts:370-378`
- **问题**：私有角色（`pub=false`）时 `relCharId = cpdId`（`character_player_data` 的 id），随后 `INSERT INTO location_npc_access ... character_id = relCharId`。而 `location_npc_access.character_id` 是 `REFERENCES characters(id) ON DELETE CASCADE` 的外键——`cpdId` 不在 `characters` 表中，**任何私有角色创建都触发 `FOREIGN KEY constraint failed`**。
- **注意**：`relationships` 用同一 `relCharId=cpdId` 却不报错（`relationships.character_id` 无 FK），所以只有 `location_npc_access` 这一步崩。
- **结果**：私有 NPC 创建流程在插入 location_npc_access 处崩溃，角色建不出来。
- **补充：前端无入口，私有创建是半成品**：唯一的玩家角色创建入口是 SmsApp 的"召唤NPC"（`SmsApp.tsx:520`），其 finalize **写死传 `true`**（`SmsApp.tsx:472` `api.finalizeCreation(creationSession, true, ...)`），前端**没有任何 UI 控件**让玩家选择公开/私有 → 实际玩家永远只建公开角色，私有路径无法从正常 UI 触发。另一编辑器 `CharacterEditModal` 是编辑已有公共角色（`forkCharacter`），非新建入口。因此：后端私有分支写了一半、前端无入口、且即便触发也因 FK bug 崩溃。
- **修复**：① 前端加"公开/私有"选择控件并传真实 `isPublic`（若要暴露该功能）；② 私有角色不写 `location_npc_access`（或改成引用真实 characters 记录）；③ 整个 finalize 加事务。
- 状态：❌ 未修复（可能设计上本就不打算对外暴露私有创建，需产品确认）

### 3. memory.ts 约会收尾折叠无限循环写重复记忆
- **位置**：`apps/server/src/lib/memory.ts:323,360 vs 118-124`
- **问题**：
  - `_foldChronicleImpl`（约会收尾折叠）循环用 `WHERE session_id=? AND summary_type='segment'` 判断已折叠进度（`foldedUpTo`），但实际写 chronicle 段落的 `foldMessages` INSERT（L118-124）**根本不写 `summary_type` 列**（schema 默认 NULL）。
  - → `summary_type='segment'` 永远查不到 → `foldedUpTo` 恒为 0 → `for(;;)` 每次迭代都取 `rowid>0` 的**同一批前 10 条消息**，反复折叠、反复插重复 chronicle、反复 embed。
  - **只要 LLM 调用不抛异常就无限循环**（只有 LLM 抛错时 catch 才 break，L350）。
  - 对比：`maybeFoldIncremental`（L190-191）不带 summary_type 过滤，滚动折叠正常——**仅收尾折叠坏**。
- **修复**：`foldMessages` 的 INSERT 补 `summary_type='segment'`（与 L432 的 session 写入对齐）；循环内基于本次写入的 `msg_end` 前移 `foldedUpTo` 而非每次重查；加最大迭代/去重保护。
- 状态：❌ 未修复（REVIEW.md 旧版未覆盖此条）

### 12. 概率公式与注释不符

### 13. computeInterval 间隔指数爆炸
- **位置**：`proactive.ts:44-103` `computeInterval`

- **修复**：friendMultiplier 用 `Math.log`/开方/封顶；decay 设上限。
- 状态：❌ 未修复
