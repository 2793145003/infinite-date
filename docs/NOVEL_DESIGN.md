# 互动小说玩法 · 设计文档

> 状态：核心决策全部锁定 + 前后端均已实现（2026-08-30）
> 讨论日期：2026-08-26
> 关联：DESIGN.md（主设计）、DATA_MODEL.md（数据模型）、CODE_MAP.md（代码索引）

---

## 一、一句话定位

**互动小说 = 和 AI 一起写小说。**

玩家以第三人称作者视角写一段，AI 把它忠实润成小说笔法（可选）、再续写下一段（旁白 + "引号对话"交织）。故事走向由玩家和小说角色共同决定。没有结尾、没有章节、没有预设剧情节点，只有「设定 + 开场」，写到哪算哪，除非玩家自己写下结尾。

---

## 二、核心体验

- 玩家进一部小说，先读到**开场**（世界观 + 初始情境），然后开始写。
- 玩家写一段（自由输入，可以是动作、对白、叙述、口语，甚至一句意图，粗糙没关系）。
- AI 接住：续写后续剧情（旁白 + 角色的引号对白）。润色是**独立功能**——玩家可先把自己写的段润色、查看、编辑满意后再定，也可以不润色直接续写。
- 阅读形态是**连续小说文本流**（像电子书），不是聊天气泡。
- 多个角色**群像**登场，不硬分线：谁在故事里出场、怎么互动，由玩家写的内容 + AI 判断共同决定，像真小说一样按剧情需要出场。
- 玩家可以**控制出场名单**：一排角色头像，亮的参与剧情、暗的不参与。讨厌谁就点暗他，故事里他就「有事不在」。

## 三、已锁定的设计决策

| 决策 | 结论 |
|---|---|
| 引擎 | **不复用**现有点名版场景引擎，新做「小说共写引擎」 |
| 角色来源 | **不复用**现有约会角色；小说自带原创角色 |
| 角色人设 | **简单人设**（性格 / 说话风格 / 与主角关系 / 底线 / 秘密，一两段话）+ **外貌描述**（供配图 / 立绘 + LLM 续写时描写外貌），防止上下文溢出，不用完整角色卡 |
| 角色毕业 | **永不毕业**，不进约会 / 行程 / 短信 / 朋友圈，永远隔离在小说内 |
| 剧情框架 | 只有**设定 + 开场**，无结尾、无章节、无关键节点 |
| 多角色组织 | **群像**，无硬分线 |
| 视角 | **第三人称**（「她 / 他」），玩家是作者 |
| 主角身份 | **默认 = 玩家本人**（名字用玩家名、代词跟玩家性别），叠加「小说设定的玩家身份 / 处境」（如「被塞进男团当队长」），不另设角色 |
| 玩家占位符 | 设定字段（简介 / 世界观 / 玩家身份）里指代玩家本人一律用 `{{player_name}}` 占位标记：前端显示为【玩家】（编辑页有「玩家」按钮一键插入），后端存 `{{player_name}}`；正文类 prompt（续写 / 润色 / 开场）注入时展开成玩家昵称，roll 类保留该标记让 LLM 沿用生成新设定 |
| 润色 | **独立功能**：玩家写完一段可选「润色 / 不润色」；润色 = AI 打磨这段（忠实原文、只改措辞不扩写），玩家可**单独查看、编辑**润色结果后再定；续写是另一个独立动作 |
| 出场名单 | **玩家可控**：一排角色头像，亮=参与剧情、暗=不参与；点暗后该角色故事里「有事不在」，玩家提到他时由其他角色解释去向 |
| 文本形态 | 连续小说流（大量旁白 + "引号对话"），不是气泡 |
| 写作方式 | 接力写：玩家一段 → AI 续写一段。**润色是独立功能**（见下），与续写分开 |
| 多周目 | **可新开一局**：写结尾（ended）后，同一部小说可另开一条新故事线 |
| 创建 / 归属 | **和剧本一样，玩家创建**：作者=创建者，`draft` / `published`，不消耗权限，只能编辑 / 删除自己的，可玩别人发布的小说 |
| roll 生成 | **对齐剧本逐字段 roll**：世界观 / 玩家身份 / 角色 / 开场都支持「手填 或 roll」，roll 基于已填字段让 AI 生成 |

## 四、与其他玩法的隔离（最重要的一条）

现有约会系统的「角色」是全局共享的活人，挂在 characters / character_instances / relationships 上，有行程、主动短信、朋友圈、好友、记忆——一整套「会自己过日子」的体系。

互动小说的角色是**小说的组成部分**，不是主城里的活人。两者必须彻底隔离：

- 角色不进 `characters` 表，不进 `character_instances`，不进 `friendships`，不进 `relationships`。
- 不参与行程系统（schedule）、主动消息（proactive）、朋友圈（moments）。
- 角色数据只存在小说自己的表里，只在小说的阅读 / 写作界面内可见。

反过来，现有约会 NPC 也不进小说（除非某天专门设计「现有角色客串某部小说」的玩法，当前明确不做）。

## 五、数据模型（新表）

> 权威实现仍在 `apps/server/src/db/schema.ts`，下表为设计稿。

### novels — 小说（对齐剧本 scenarios 的创建 / 归属模型）

```sql
CREATE TABLE IF NOT EXISTS novels (
  id            TEXT PRIMARY KEY,
  author_id     TEXT,                            -- 创建者（对齐剧本 author_id），玩家删号置 NULL，小说保留
  title         TEXT NOT NULL,                   -- 标题
  summary       TEXT NOT NULL DEFAULT '',        -- 一句话简介（列表页展示）
  world_setting TEXT NOT NULL DEFAULT '',        -- 世界观 / 背景设定（LLM 会读）
  protagonist_setting TEXT NOT NULL DEFAULT '',  -- 玩家身份 / 处境（玩家在这部小说里的身份设定，LLM 会读）
  opening       TEXT NOT NULL DEFAULT '',        -- 开场文本（玩家进入即读到，故事起点）
  cover_url     TEXT,                            -- 封面图（可选）
  status        TEXT NOT NULL DEFAULT 'draft',   -- 'draft' 草稿 / 'published' 已发布
  play_count    INTEGER NOT NULL DEFAULT 0,      -- 游玩次数（对齐剧本）
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_novels_author ON novels(author_id);
CREATE INDEX IF NOT EXISTS idx_novels_status ON novels(status, created_at);
```

### novel_characters — 小说角色（简单人设）

```sql
CREATE TABLE IF NOT EXISTS novel_characters (
  id          TEXT PRIMARY KEY,
  novel_id    TEXT NOT NULL REFERENCES novels(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,
  gender      TEXT NOT NULL DEFAULT '',          -- 性别：'female'/'male'/''（空=未指定，LLM 按人设自由发挥）
  persona     TEXT NOT NULL DEFAULT '',          -- 简单人设：性格 / 说话风格 / 与主角的关系 / 底线（一两段话，控制长度）
  appearance  TEXT NOT NULL DEFAULT '',          -- 外貌描述（供配图 / 立绘 + LLM 续写时描写外貌）
  created_at  INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_novel_chars ON novel_characters(novel_id);
```

### novel_sessions — 玩家在某部小说的故事线（多周目）

```sql
CREATE TABLE IF NOT EXISTS novel_sessions (
  id             TEXT PRIMARY KEY,
  player_id      TEXT NOT NULL REFERENCES players(id) ON DELETE CASCADE,
  novel_id       TEXT NOT NULL REFERENCES novels(id) ON DELETE CASCADE,
  status         TEXT NOT NULL DEFAULT 'active',   -- 'active' 进行中 / 'ended' 玩家已写结尾
  excluded_chars TEXT NOT NULL DEFAULT '[]',       -- JSON 数组：被点暗（不参与剧情）的角色 id，默认空=全部参与
  story_overview TEXT NOT NULL DEFAULT '',         -- 故事进展总览（三折叠长期层；增量更新：旧总览 + 滑出中期的段摘要 → 新总览）
  overview_upto  INTEGER NOT NULL DEFAULT 0,       -- 总览已折进到第几段（display=1 序号），防重复折叠
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_novel_sessions ON novel_sessions(player_id, novel_id);
```

> 主角 = 玩家本人：名字读 `players.name`，第三人称代词跟 `players.gender`（female→「她」/ male→「他」），不单独存字段。
> 多周目：一个玩家对一部小说可有多条 session（每局一条）。同小说最多一条 `status='active'` 进行中，写结尾（ended）后可另开新局。

### novel_turns — 接力写的段落

```sql
CREATE TABLE IF NOT EXISTS novel_turns (
  id          TEXT PRIMARY KEY,
  session_id  TEXT NOT NULL REFERENCES novel_sessions(id) ON DELETE CASCADE,
  role        TEXT NOT NULL,                      -- 'player' 玩家原文 / 'assistant' AI 续写（润色开时含润色后的玩家内容）
  text        TEXT NOT NULL,                      -- 该段文本
  summary     TEXT NOT NULL DEFAULT '',           -- 该段事件摘要（三折叠中期层；空=尚未折叠）。折叠时只专门保留「未揭示的悬念/线索」，其余自然概括
  display     INTEGER NOT NULL DEFAULT 1,         -- 是否在正文中显示（润色开的玩家草稿=0）
  created_at  INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_novel_turns ON novel_turns(session_id, created_at);
```

> 润色开：玩家草稿落 `role='player', display=0`（保留原文备查，不显示），AI 输出落 `role='assistant', display=1`（润色 + 续写）。
> 润色关：玩家原文落 `role='player', display=1`（正文显示），AI 续写落 `role='assistant', display=1`。
> 小说「正文」= 按时间序拼接所有 `display=1` 的段落。

## 六、出场名单（玩家可控）

玩家可以控制每一局里「哪些角色参与剧情」。

- **交互**：写作页上方（或下方等其他位置）一排角色头像。**头像亮着 = 参与剧情，暗着 = 不参与剧情**。点亮 / 点暗状态持久存在 session 上，随时可改，影响后续所有段。
- **数据**：`novel_sessions.excluded_chars`（JSON 数组，被点暗的角色 id）。默认空数组 = 全部参与。用「屏蔽名单」而非「允许名单」，作者日后给小说新增角色时，新角色默认参与，不用改老玩家的名单。
- **引擎**：AI 写下一段时，prompt 带上「当前参与剧情的角色名单」，AI 只在名单内选人出场，被点暗的角色不出场、不被旁白提及。
- **语义（已锁定）**：被点暗的角色 = **故事里此刻不在场**（去忙别的事了），不是「不存在」。若玩家在输入里主动提到了他，AI **不让其出场**，而是由在场的其他角色自然解释他的去向（「他去做什么什么事了，不在」）——世界自洽，不硬消失。
- **多周目**：新局默认 `excluded_chars=[]`（全部参与），不继承上一局的状态。

## 七、引擎设计（接力写）

两个**独立动作**：润色、续写。

### 7.1 续写（核心）

```
玩家写一段（主角的戏）→ 提交续写
  → 组装续写 prompt（见「九」）
    ├─ 小说设定 world_setting + 玩家身份 protagonist_setting
    ├─ 主角 players.name + 第三人称代词（她/他，跟 gender）
    ├─ 参与剧情的角色（name + persona + appearance；被点暗的不带人设）
    └─ 故事摘要 + 最近正文（受上下文预算约束，见「八」）
  → LLM 续写下一段：只写角色们的反应和对话 + 环境氛围
  → 落库 novel_turns（role='assistant'）
  → 前端追加显示
```

**主角由玩家写，AI 只写世界**（核心定位，实测锁定）：AI 续写里主角的任何动作、对话、心理、感受都**不出现**——连「她看向众人」「她感到压力」都不写。AI 只写其他人（角色们）的反应和对话 + 环境氛围。玩家写主角的戏，AI 写角色的戏，各写各的，接力推进。

**停点 = 角色反应告一段落**，不是「主角回应之前」。写到角色们反应完就停，把笔交回给玩家。

### 7.2 润色（独立功能）

```
玩家写了一段 → 点「润色」
  → 组装润色 prompt（见「九」）
  → LLM 忠实打磨：不改内容、不删减、不添加，只把文字写得更流畅
  → 返回润色结果，玩家可单独查看、编辑，再决定用不用
```

要点：

1. **忠实扩写，不是改写**。润色时 AI 把玩家的动作 / 对白 / 叙述「写得像小说」，但不能删掉玩家写的内容、不能改变玩家想表达的走向。玩家体验高于一切——玩家写进去的东西就是故事的一部分。
2. **无编造剧情压力**。没有「推进到下一个节点」的任务，AI 只负责自然地把故事接着写下去，节奏可以慢、可以留白，不硬推。
3. **出场名单是硬约束**：被点暗的角色 AI 不主动写他出场；玩家提到时，由在场角色解释其去向，而非让他出场。

### 7.3 撤回 / 重试 / 继续（末尾栈式）

三个操作全部退化成「末尾」语义，摘要随段走、不单独维护：

| 操作 | 语义 | 数据动作 |
|---|---|---|
| 继续 | 追加下一段（玩家写 → AI 续写）| 追加 turn（已有）|
| 撤回 | 删最后一段，可连续撤回多次 | 删末尾 turn（原文 + summary 一起删）|
| 重试 | 对最后一段 AI 续写不满意，重新生成 | 删末尾 assistant turn → 重新续写 |

- **撤回**：只删末尾、可连续点，一直撤到只剩开场。**不动总览**（见「八」），残留一两句旧信息无害。
- **重试**：等价于「撤回最后一段 assistant + 用现有上下文重新续写」。玩家刚写的那段 player 保留。
- **边界**：撤回到总览覆盖的段时，总览不动。极端场景（撤回为推翻主干剧情）会让 AI 短暂按旧方向写，玩家再撤/重写即纠正；真要兜底，以后加「连续撤回超过阈值才重生成总览」，现在不做。
- 前端交互：正文流末尾一段悬停/点击出现「撤回」「重试」；已提交内容可回退，但不能编辑中间段（改中间段 = 撤回到那一点重写）。

## 八、上下文管理（三折叠，对齐约会 turn-memory，单位=段）

约束：角色只带简单人设；正文越长越不能全塞进 prompt。

**固定部分**（每次都带）：小说 world_setting + 玩家身份 protagonist_setting + 参与剧情的角色简单人设 + 主角（玩家名 / 性别）。被点暗角色的简单人设省略。

**正文部分**——三层折叠：

| 层 | 内容 | 存哪 | 注入位置 |
|---|---|---|---|
| 热窗（最近 N 段）| 原文 | novel_turns.text | `recent_text` 尾部 |
| 中期（再往前 M 段）| 段摘要（每段一句话）| novel_turns.summary | `recent_text` 头部 |
| 长期（更早）| 故事总览（一条）| novel_sessions.story_overview | `summary` 槽 |

- 参数 N（热窗段数）、M（中期摘要段数）实测调，N=5 / M=20 起步。
- **段摘要生成**：每段续写后异步生成（LLM，一句话），挂在 turn.summary 上。折叠时**只专门保留「未揭示的悬念 / 线索」**，其余剧情自然概括——不钉关系数值、不钉玩家事实。
- **段摘要保时间**：摘要须保留「发生的时间与地点」。生成时把本段之前的最近几段（已有摘要用摘要、否则用原文）作为前文喂入，供推断正文未显式写出的时间——本段显式写了用本段、内容暗示推进（睡醒/天黑）则推断新时段、否则延续前段。不写死三档规则，只说「提取时间」，靠模型看前文自行推断。
- **总览增量更新**：段摘要滑出中期窗口（超过 M 段）时，把滑出的摘要折进总览——「旧总览 + 一批滑出摘要 → 新总览」，不全量重写。总览同样保留当前的时间与地点线索。

**撤回与总览的一致性（已锁定）**：撤回**不动总览**。总览是高度压缩的远期摘要，撤回末尾段最多让总览残留一两句已撤段的旧信息——这是「多信息」不是「缺信息」，无害（AI 顶多提一嘴已撤回的事，后续总览增量更新时自然消化）。相较「总览丢悬念」这种致命错误，可接受。

- 角色「简单人设」的定位：不是完整角色卡，只是一两段话给 LLM 锚定性格和说话方式。随故事发展，角色的新变化靠「故事摘要」承接，不回写人设。

## 九、Prompt 设计（已锁定）

### 核心定位（多轮实测收敛）

1. **互动小说首先应该是个好看的小说**。续写第一目标是「写好、让人想读下去」，不是「反应正确」。群像、悬念、氛围都服务于好看。
2. **主角由玩家写，AI 只写世界**。AI 续写里主角的任何动作、对话、心理、感受都**不出现**——连「她看向众人」「她感到压力」都不写。AI 只写角色们的反应和对话 + 环境氛围。
3. **停点 = 角色反应告一段落**，不是「主角回应之前」。
4. **正面表述，不列禁令**。每发现一个问题就加一条「不要XX」会堆成军规（曾到 11 条），反而更糟。用正面原则 + 精准点名（禁选项时精确点名「A. B. C. 行」才压得住）。

### 续写 prompt（novel.continue.txt）

```text
你是一位小说家，和玩家一起写这部连载小说。玩家写一段，你接着写下一段，轮流往下写。

世界观：{{world_setting}}
主角：{{player_name}}，{{protagonist_setting}}，第三人称用「{{pronoun}}」。
角色：
{{characters}}

目前的故事：{{summary}}

最近的正文：
{{recent_text}}

接着写下一段，把它写好——环境、人物、对话、情绪都写到位，让人想读下去，剧情也顺理成章。

主角由玩家来写。你只写其他人（角色们）的反应和对话、以及环境的氛围——主角的动作、对话、心理都留给玩家。

写到角色们的反应告一段落，就停在这里，把笔交回给玩家。

只输出正文。
```

### 润色 prompt（novel.polish.txt）

```text
你是一位小说编辑。把玩家写的这段润色成流畅的小说文字。

世界观：{{world_setting}}
主角：{{player_name}}，{{protagonist_setting}}，第三人称用「{{pronoun}}」。
角色：
{{characters}}

玩家写的段落：
{{player_input}}

忠实原文：不改内容、不删减、不添加，只把文字打磨得更流畅自然。第三人称，对话加引号。

只输出润色后的段落。
```

### roll 模板

- **novel.roll.txt**：通用字段 roll（世界观 / 玩家身份），仿 scenario.roll.txt，列已有设定 + 输出目标字段 JSON。
- **novel.roll-characters.txt**：roll 角色数组，要求「性别不限、表里反差、有秘密有底线、性格不重复」。
- **novel.roll-opening.txt**：roll 开场（含禁选项规则）。

### 已实测锁定的经验

- **禁选项**：泛泛说「不要给选项」无效；精准点名「A. B. C. 开头的行」「[请选择]」「【请选择】」「反问玩家」才压得住。更优的是正面「把笔交回给玩家」。
- **接力信号清理**：gemma 会在结尾自发写「（轮到你了）」「请接龙」等元文本（非正文、非选项），实现时在输出后剥掉这类结尾（cleanNovelText）。
- **AI 味比喻 / 偶发语病**：gemma 底子问题，不靠加规则压（会重蹈军规覆辙），靠温度微调 + 玩家重 roll / 编辑兜底。
- **主角越界（残留问题）**：「林知夏感觉到压力」「她该如何回应」这类主角心理/反问，靠「停点=角色反应告一段落」压住，已清干净。

## 十、前端

- **入口**：心动终端（web-v4）新增「小说」入口（tab 或图标），不进现有约会 / 短信 / 地图体系。
- **小说列表页**：标题 + 封面 + 一句话简介 + 角色名单；「我的 / 公开」两个页签（对齐剧本）。
- **小说创建页**：玩家自建（标题、简介、世界观设定、玩家身份、开场、角色名单 + 每人简单人设 + 外貌描述）。世界观 / 玩家身份 / 角色 / 开场均支持「手填 或 roll」。
- **roll 依赖顺序**（对齐剧本逐字段 roll）：世界观 →（依赖标题+简介）；玩家身份 →（依赖标题+简介+世界观）；角色 →（依赖世界观+可选「方向」如几个/什么类型）；开场 →（依赖世界观+玩家身份+角色，最后 roll）。
- **阅读 / 写作页**（核心界面）：
  - 上方：连续小说正文流（阅读器式，段落滚动，旁白正常字体、"引号对话"可轻微区分但保持小说形态）。
  - 一排角色头像开关（亮=参与、暗=不参与，点按切换，位置可在正文上方 / 下方等）。
  - 输入区：一个输入框 + 一个「润色」开关。玩家写一段，选择是否润色，提交后 AI 流式续写并追加到正文。
  - 可回滚浏览全文；写结尾时玩家自行标记结束，可另开新局。

## 附录：Gemma 可行性验证（2026-08-26）

**结论：Gemma-4-26B（vLLM，max_model_len=16384）完全撑得起本玩法，无需换模型。**

三个核心 case 裸调验证全部通过：

| Case | 验证点 | 结果 |
|---|---|---|
| 润色 + 续写（群像） | 忠实扩写玩家输入 + 第三人称小说笔法 + 角色说话风格锚定 + 群像留白 | ✅ 输出地道连载小说，人设不跑偏 |
| 出场名单（点暗顾清晏） | 玩家提到被点暗角色 → 不出场，由他人解释去向 | ✅ 伙计解释「去隔壁县唱堂会了」 |
| 润色关（只续写） | 玩家原文原样保留，AI 只在后面续写 | ✅ 原文不动，续写自然 |

Token 消耗：输入约 420~450、输出约 440~600。

**验证用 prompt 结构雏形**（实现时以此为基础）：
- system：世界观 + 主角（第三人称「她」，指代玩家）+ 角色简单人设（每人一两句话，含性格/说话风格/底线）+ 写作铁律（大量旁白 + 引号对话、第三人称、忠实扩写、续写一段留白）。
- 出场名单通过「当前这一轮谁被点暗 + 铁律约束（不出场、不被旁白正面描写、提到由他人解释去向）」注入。

**注意事项（实现时 prompt 措辞需精确）**：被点暗的角色，旁白不正面写其出场/神态，只允许在他人的对话里带过名字和去向——否则会出现「见多识广、心思缜密的顾清晏」这类旁白擦边。
