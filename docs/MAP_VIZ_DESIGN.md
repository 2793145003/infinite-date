# 可视化地图 — 实现方式文档（讨论稿）

> 状态：讨论稿 v2（5 项决策已确认，未实施）。
> 目标：把「列表式地图」改成「图形化交互地图」——凹多边形区域拼块、逐层下钻。
> 背景：dsh 曾用 d3-delaunay + sharp 私自改造旧 `MapApp.tsx`（已归档文件），未讨论、乱装依赖，已回滚。本文是正经的、先讨论后实现的方案。

## 1. 目标形态（星落描述）

- 一张**能点的图**：主题背景色上用高亮色描边出**凹多边形边框**，半透明填充，切成若干块，每块 = 一个地点。
- **每个地点区域中心**浮一张毛玻璃小卡片，显示该区域名字 + 简介开头。
- **点击**某区域 → 该区域高亮；**子区域不显示**（进入该地点才看得到子区域）。
- **布局**：上半部分是地图，下半部分是毛玻璃信息卡（地区名字 + 简介 + 分割线 + 「这里有谁」 + 探索入口）。
- **进入**：选中区域后，点「进入」按钮（放地区名字旁），以该区域轮廓为边界，内部再切出子区域，逐层下钻。

## 2. 现状

- **当前页面**：`apps/web/src/pages/SceneMapApp.tsx`（`View = scenemap`），列表卡片式。点卡片 → `SceneLocation`（地点详情/决策页，含探索）。
- **数据**：`scene_locations` 表，**无坐标**，只有 `parent_id`（树形层级）、`name`、`summary`、`background_image`、`npcs`（路人）、`activities`。
- **规模**（主城 `default-world`，排除 `mission-*` 任务世界）：
  - 顶层地点（`parent_id IS NULL`）：**6 个**
  - 子地点总数：104 个
  - 总数 110，层级约 2–3 层
  - **背景图现状**：110 个地点里仅 **5 个**有 `background_image`（全是子地点、玩家上传）；**顶层 6 个区域全部无背景图**
- **现成 NPC 数据源**：`GET /scene/map/npcs`（`sceneMapNpcs()`），返回 `locations: Record<locationId, npcs[]>`，已含头像/可见性/正在做什么。`SceneMapApp` 已有 `collectChars()` 递归聚合子地点角色的逻辑，可复用。

## 3. 核心设计：分层 Voronoi 分割（自下而上，不手绘）

**算法**：每一层，以「父区域的多边形轮廓」为边界，把它的子地点用**泰森多边形（Voronoi）**切成若干块，每块归一个子地点。

- **顶层**：主城轮廓由算法生成（见下），7 个顶层地点在轮廓内切 7 块。
- **下钻**：进入某区域，以该区域的多边形为边界，其 K 个子地点切 K 块。
- **叶子地点**（无子地点）：不分割，「进入」直接跳地点详情/探索。

**主城轮廓（关键决策：不手绘，算法生成）**：星落不会画地图、也不该画。轮廓取顶层地点种子点的**凸包（convex hull）**，可选「按固定种子抖动顶点」得到不规则凹多边形。这样：
- 顶层 7 个地点自动被「包」进主城边界，无需任何人画图。
- 抖动后边界不规则，有「真实地图」的轮廓感。

**「加地点，地图变不变」——会变，但可控且确定**：
- 加一个**顶层**地点 → 顶层重切（7 块 → 8 块）。
- 加一个**子地点** → 只影响它所属父区域内部（**局部重切**，其它块不动）。
- **确定性**：同一组地点，每次打开地图切出的块**完全一样**（地点 ID 定种子，见 §6）。地图不会「今天这样明天那样」，只有地点增删才变。
- 这正是「简单规则 + 自下而上涌现 + 不需要管」：地点决定地图，人和管理员都不维护布局。

**凹多边形的来源**：Voronoi 天然产生**凸**块；把块**裁剪到凹的父轮廓**后，贴边块自然变凹、内部块保持凸。整体 = 不规则多边形拼图（真实行政区划图 / 游戏区域图），棱角分明。

## 4. 视觉设计

| 元素 | 设计 |
|---|---|
| 区域块 | 主题色系**半透明填充** + **高亮色描边**（描边即「凹多边形边框」），棱角分明、不圆角 |
| 选中态 | 选中区域填充透明度提高（更实）+ 描边加亮/加粗；其余维持半透明 |
| 区域标签 | **每块中心都常驻一张毛玻璃小卡**：未选中 = **半透明毛玻璃**；选中 = **高亮色毛玻璃**（更突出）。显示名字 + 简介开头（超长截断） |
| 主城轮廓 | 算法生成（凸包 + 可选固定种子抖动，见 §3），不手绘 |
| 颜色 | 各块可用同色系不同明度区分，或统一半透明主题色；实现时按当前主题 `--card-bg-*` / accent 色取 |
| 背景图 | **有则显示**：把该地点的 `background_image` 裁成区域多边形形状，叠一层半透明主题色蒙版（保证文字可读 + 统一色调）；**无则纯主题色填充**。现状仅 5 个地点有图 → 背景图是「锦上添花」，主体仍是主题色填充 |

> 毛玻璃教训（沿用既有 ref）：`backdrop-filter` + 真 rgba 半透明变量（`withAlpha` 如 `--card-bg-strong`）；`opacity+::before` 与 `color-mix` 在 QQ webview 不可靠。半透明底用 ~0.15，别用 0.6（太实）。

## 5. 布局与交互

**布局**（手机壳 430px 内）：
```
┌─ appbar（← 地图）─────────────┐
│  上半：SVG 地图（多边形区域拼块）│
│  （每块中心浮毛玻璃小标签）      │
├───────────────────────────────┤
│  下半：毛玻璃信息卡             │
│   · 地区名字  [进入]（名字旁）  │
│   · 简介                       │
│   ──分割线──                   │
│   · 这里有谁（分两组，见下）    │
│   · 探索 入口                  │
└───────────────────────────────┘
```

**交互**：
1. 进入地图 → 显示顶层 7 块，无选中态（或默认选第一块）。
2. **点击**某区域 → 高亮选中，下方信息卡更新。**子区域不显示**。
3. 点**「进入」**（名字旁）→ 有子地点：以该区域轮廓为边界切出子区域、下钻；**叶子地点：直接进 `SceneLocation`**。面包屑/返回按钮回上层。
4. **「探索」**（信息卡里）→ 直接进 `SceneLocation`（详情/探索），与列表式「点卡片」行为**完全一致**。

**「这里有谁」——本区域 + 子地点，都要显示，分开显示**（两组）：
- **「在这里」**：该区域直接在场的角色/NPC。
- **「在子区域」**：子地点里的人，按子地点分组列出。
- 点头像仍可看行程（复用现有 ScheduleModal）。

## 6. 技术方案

- **渲染**：前端 **SVG**（`<path>` 多边形 + `onClick` + `fill/opacity/stroke`）。拼图地图用 SVG 最合适——点选、高亮、缩放都是原生能力，无需 Canvas 手写命中检测。**不需要 sharp**（那是 dsh 生成静态 PNG 用的，交互式 SVG 用不上）。
- **几何库**：`d3-delaunay`（轻量 ~10KB）——`Delaunay.from(points).voronoi()` 生成 Voronoi 多边形坐标；**裁剪**用小型 polygon-clipping 库（实现时定）。
- **种子点生成（确定性）**：每个地点一个种子点，位置由「地点 ID hash → PRNG（mulberry32）→ 在父轮廓内撒点」。**固定 seed = 每次切一样**，且**不需要给数据库加坐标字段**。
- **凸包/抖动**：凸包可直接用 d3 或手写 Andrew 单调链；抖动用同一 PRNG 保证确定。
- **毛玻璃**：复用现有 `backdrop-filter` 体系（见 §4 注）。
- **默认列表，图形 opt-in**：图形版做成独立视图 `SceneMapViz`，`SceneMapApp` 顶部加「图形 / 列表」切换，**默认列表**。星落先自己切到图形版看效果，绝不让别人的前端因这个改动挂掉。

### 生成时机、性能与确定性（实测 2026-08-17）

- **生成时机 = 前端打开地图时实时现算，不预生成、不缓存、不共享全局状态**。没有「全局地图」这个共享资产，也就不存在「变动时全局重新生成」。每个玩家每次打开，用自己的可见地点集（`/scene/locations` 已过滤）+ ID 定种子，在浏览器里现算。
- **可见性隔离天然成立**：A 建私有地点 → 只改变 A 的可见地点集 → 只有 A 的地图变；B 的点集没动 → B 完全不变。无需锁/缓存/后端协调。
- **速度（d3-delaunay 实测）**：Voronoi 分割 + 提取全部多边形坐标——顶层 3~5 块 ≈ **14 µs**；子层 20 块 ≈ 36 µs；主城全 104 个地点一次性算完 ≈ **105 µs（0.1 ms）**。对比一次 HTTP 请求 10~100 ms，几何计算是它的 1/100~1/1000，可忽略。耗时大头是数据拉取（列表式已在拉，不新增）。
- **确定性**：同一地点集每次算出来**逐位一致**（实测 104 点两次结果 JSON 完全相同）。种子点由地点 ID hash 定、算法纯函数，同输入同输出，无需缓存。仅地点增删才变。
- **一次性计算**：地图只在「打开页面」「下钻一层」各算一次，结果存 state；滚动/高亮/hover 不重算。

## 7. 数据模型（结论：不改 DB）

- **不需要给 `scene_locations` 加坐标列**。布局完全由算法确定性生成，地点增删后自动重切，无需人工摆放。
- 只读现有字段：`parent_id`（层级）、`name`、`summary`、`background_image`（有则裁成区域形状 + 半透明蒙版，无则主题色填充）。
- **可见性过滤（不同玩家地图不同）**：后端 `/scene/locations` 与 `/scene/map/npcs` 已按「`world_id='default-world'` + `(is_public=1 OR creator_id=当前玩家)` + 排除 `temp-`」过滤。图形版**直接复用这两个端点**即自动获得正确可见性——私有地点（`is_public=0`）只有创建者看得到，所以每个玩家的地图 = 公共地点 + 自己的私有地点，各不相同。前端**不额外做可见性判断**（另写反而容易漏，复用 API 即可）。

## 8. 已确认决策（v2 固化）

1. **区域标签**：每块都常驻；未选中 = 半透明毛玻璃，选中 = 高亮色毛玻璃。
2. **主城轮廓**：算法生成（凸包 + 可选抖动），**不手绘**；加地点会触发重切（顶层=整体、子地点=局部），同一地点集永远稳定。
3. **这里有谁**：本区域 + 子地点都显示，**分开两组**。
4. **替换 vs 并存**：并排跑，**默认列表**，图形版 opt-in，星落自己先看。
5. **探索入口**：与列表式行为一致（进 `SceneLocation`）。实施时做功能对照，缺失则提醒。
6. **可见性过滤**：沿用现有 API 的 `is_public=1 OR creator_id=玩家` 过滤，不同玩家地图不同（私有地点仅创建者可见）。图形版与列表版看到的地点集天然一致。
7. **生成时机**：前端打开地图时实时现算，不预生成、不缓存、不共享全局状态；一个玩家建私有地点不影响别人的地图（隔离天然成立）。
8. **布局重排**：允许公共地点位置随可见地点集增减而重排（选简单方案）。无限流主城「空间流动」本是世界观的一部分——不同玩家看到的布局不同，是特性不是 bug，无所谓。
