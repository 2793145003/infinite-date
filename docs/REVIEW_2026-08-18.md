## 一、安全 / 数据完整性（亲验）

### S-1 🔴/🟠 P1 — per-player LLM `base_url` → SSRF + 共享 key 外泄
**文件**：`llm/adapter.ts` L45-59 (`getEffectiveLlmConfig`)、L178-202 (fetch)；`routes/settings.ts` L28-55 (PATCH `/settings`)
**已复验**：V5 的 🔴-2（全局写 `app_settings.llm_config`）**已修复**——现在是 per-player 的 `player_llm_configs`，GET 脱敏。但新路径仍危险：
- `getEffectiveLlmConfig`：`apiKey = dbConfig.apiKey || config.llmApiKey`。玩家只填 `base_url`、留空 `api_key` 时，生效 key **回落为全服共享的环境变量 `LLM_API_KEY`**。
- fetch 把 `Authorization: Bearer <共享key>` 发到 `baseUrl + /chat/completions`，而 `base_url` **无任何 scheme/主机校验**（不强制 https、无域名白名单、不拦 localhost/RFC1918/内网 metadata 地址）。
- `/tokenize` 预检（L130-135）同样打到玩家 URL。

**影响**：多人联机部署下，任一登录玩家可把 base_url 指到自己服务器，让**后端携带全服共享 LLM key + 完整 prompt/角色卡内容**转发过去（凭据外泄 + 内网 SSRF）。默认 `.env.example` 的 key 是 `sk-placeholder`（自托管本地 vLLM 是占位符，此场景无实际密钥）；**只要换成真实共享 key，即构成利用**。
**修复**：① 玩家设置了自定义 `base_url` 时必须自带 `api_key`，**不要**回落共享 key；② 对 `base_url` 做校验（强制 https + 可信域名白名单，拒绝 `file://`、`localhost`、内网/cloud-metadata 地址）。

### S-2 🟠 P1 — 场景撤回/整场删除不删 `scene_message` embedding，已撤回对话仍被语义检索「记住」
**文件**：`lib/scene-rollback.ts` L133-199（`deleteAppendedRows` / `deleteAllAppendedRows`）
**已复验**：`scene-wiring.ts` L746/785 用 `storeEmbedding(..., 'scene_message', <msgId>, ...)` 存对话原文向量，作为语义检索「对话原文」通道；但回滚时：
- `deleteAppendedRows`（单轮撤回/重试）删 `scene_messages` 行，**只联删 fold/fact 的 embedding**（L156-163），从不删 `source_type='scene_message'` 的 embedding；
- `deleteAllAppendedRows`（整场删）同样删行不删对话 embedding（L178）。

**影响**：undo/retry 或整场删除后，被删掉的台词仍留在 `memory_embeddings`，会被 NPC 语义检索到并「回忆/复述」，与「撤回=当没发生过」的语义矛盾。
**修复**：两个删除路径都补删对应 `scene_message` source_id 的 embedding。

### S-3 🟠 P1/P2 — 世界任务奖励发放非原子（claim 与发放分离）
**文件**：`routes/mission.ts` `evaluateWorldMission` L892-924
`evaluation_result IS NULL / changes===1` 的原子 claim 是对的（防并发双发），但 `grantPlayerPermission` / `grantCharacterPermission` / `rating_score` 更新是**事务外**的多次独立写。claim 与发放之间崩溃 → 任务已标记完成但奖励没发，且 claim 已消费导致无法重试；`changes===0` 时仍会再次 rating + `sendEmail`（L919-930）。
**修复**：claim + player 发放 + NPC 发放 + rating 包进一个事务；仅 `changes===1` 时做 rating/邮件。

### S-4 🟠 文档记录 — `scene-named` 遗产引擎 `/end` 必失败（`ended_at` 列不存在）
**文件**：`routes/scene-named.ts` L226 `UPDATE scene_sessions SET ended = 1, ended_at = ?, ...`
**已复验**：`scene_sessions`（`scene-schema.ts` L55-79）有 `ended` 但**没有 `ended_at` 列**，全库唯一引用这一列、无任何 migration 补它。该 UPDATE 必抛 `no such column`，`ended` 永远置不上、`endSceneSession` 从不执行（被 `.catch` 吞掉）。
**影响评估**：前端**不调用** `/scene-named/*`（实测 grep 前端无任何 `scene-named` 引用；live 路径是 `/scene/:id/end`，scene.ts L657-671 **正确**，只写 `ended/updated_at`）。所以这是**未再驱动但已注册路由**的潜在 bug，非当前生产瘫痪。**建议给 `scene-named` 遗产引擎定日落时间或直接退役**（与 V5 G-14 的双引擎技术债一致）。

### S-5 🟢 P2 — 管理员审计身份可伪造
**文件**：`routes/admin.ts` L40/L65-68：`character_edit_log.editor_id` 取客户端 `x-player-id` 头，而非 `requireAdmin` 返回的 playerId。改为用服务端鉴权身份写入。

### 已验证无碍的关键项
